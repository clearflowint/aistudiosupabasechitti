# Global JSONB Job Registry — Batch 1

## Decision

Use one global table, `public.n8n_global_jobs`, for job tracking across ClearFlow products. Keep product-specific execution logic in separate n8n workflows. Product business data stays in its existing tables.

- One row represents one job.
- `job_id` is generated by PostgreSQL and starts at 100.
- `product_id`, `tenant_id`, `job_type`, `status`, and timestamps are searchable columns.
- `job_data` is the single JSONB document for the instruction (including `request_id`), prepared payload, recipients, per-recipient statuses, acknowledgement events, progress, errors and summary.
- No per-recipient delivery table, separate communication table, automation RPC, or generic database function is introduced.
- The PWA can read only jobs for its active product/tenant owner. n8n is the writer using server-side credentials, never browser code.

## Workflow ownership and names

The global table is not a global business workflow. Keep product-specific execution separate:

- `public.n8n_global_jobs` is the global registry; each row is scoped by `product_id` and `tenant_id`.
- **ClearFlow — JSONB Job Contract Preview (Draft Only)** is the global PWA contract preview only; it is not a CFCF business or WhatsApp workflow.
- **CFCF Automation Worker — Draft** is CFCF-specific and remains incomplete/inactive. Its legacy `cfcf_*` RPC nodes, old `n8n_whatsapp_*` placeholders, and WAHA session-inventory HTTP node have been disabled.
- **CFCF — Monthly Schedule Evaluator (Setup Required)** is CFCF-specific and remains inactive. Its HTTP nodes for rolled-back schedule/job RPCs have been disabled pending redesign against approved n8n configuration and the global registry.
- **CFCF — Shared Error Handler** is shared only across CFCF workflows, not a global cross-product error handler.
- **ClearFlow MCP Connection Test** is a connection-test utility, not a business workflow.

For WhatsApp, the selected design is a CFCF-dedicated shared number/session with CFCF-specific routing, plus a separate entry path for tenant-owned CFCF numbers/sessions. Keep inbound product routing out of a global workflow because the dedicated shared number already determines the product. The shared-number entry checks the sender against authoritative CFCF tenant/contact records before tenant-specific routing; the tenant-owned entry resolves the receiver number to a CFCF tenant and then checks the sender within that tenant. Ambiguous or unknown mappings follow the CFCF unknown-sender policy without private-data disclosure.

Do not fan out one inbound event to multiple business workflows. Do not activate any workflow from this design note. Reuse exact established names; the two separate CFCF inbound draft workflows are justified because shared-number and tenant-owned receiver resolution are different trust boundaries. The CFCF schedule evaluator remains separate from WhatsApp inbound processing. Existing PWA notification tables/functions/data/cron jobs remain untouched; do not recreate rolled-back CFCF schedule/job tables or prototype RPCs.

## Flow

1. The PWA sends the manager's instruction, product ID, tenant ID, action and selected IDs.
2. n8n validates the authenticated user's identity and confirms active owner access for the exact product/tenant before reading private data or writing a job.
3. n8n fetches authoritative data from existing Supabase tables, deduplicates recipients, and resolves the actual recipient count.
4. Before creating a job, n8n looks up the scoped `request_id`. If it already exists, return that job receipt and do not dispatch again. A unique expression index is the final race-condition guard; if a concurrent duplicate insert conflicts, fetch and return the existing job.
5. For a new approved production job, n8n creates one job row and uses the returned database `job_id` as the canonical Job ID.
6. n8n updates the same row's `status` and `job_data` as progress and acknowledgements arrive.
7. The PWA reads the row and displays progress. It does not prepare messages, reports, recipient payloads, or schedules.

## Campaign batch limit

A campaign batch contains 1–100 unique resolved contacts. n8n must reject a larger batch before any provider call. The database constraint also rejects any campaign job document that contains a `recipients` array longer than 100. Do not silently split a batch into multiple jobs.

## Example `job_data`

```json
{
  "request": {
    "action": "campaign",
    "group_ids": ["group-1"]
  },
  "progress": {
    "recipient_count": 2,
    "processed_count": 1,
    "accepted_count": 1,
    "failed_count": 0,
    "uncertain_count": 0
  },
  "recipients": [
    {"contact_id": "contact-1", "status": "provider_accepted", "updated_at": "2026-10-20T05:40:05Z"},
    {"contact_id": "contact-2", "status": "pending"}
  ],
  "events": [
    {"time": "2026-10-20T05:40:05Z", "contact_id": "contact-1", "event": "provider_accepted"}
  ],
  "result_summary": null,
  "error": null
}
```

Use statuses that reflect evidence. Provider acceptance is not proof of delivery or read. If a send outcome is uncertain, record `uncertain` and require manual reconciliation; do not blindly retry or resend.

## Update ownership

n8n is the only writer for a job's JSONB progress. Keep recipient processing and JSONB updates sequential within a job so simultaneous writes cannot overwrite one another. The PWA reads the saved document and does not mutate job state.

## Inbound queueing, sender acknowledgement, and failure policy

The separate workflows are **CFCF — Shared WhatsApp Inbound (Draft)** and **CFCF — Tenant-Owned WhatsApp Inbound (Draft)**. Both are inactive skeletons with an unauthenticated webhook placeholder, validation-only Code node, and a 503 `DURABLE_QUEUE_NOT_CONFIGURED` response. They do not persist events, resolve tenant/contact records, or send WhatsApp acknowledgements. Do not activate until ingress authentication, authoritative lookup, durable idempotent enqueue, and acknowledgement controls are implemented and tested.

Queueing is required at two distinct boundaries:

1. **Ingress queue:** validate and deduplicate the inbound provider event, resolve tenant scope, then durably enqueue before returning a successful transport response. Do not run slow business logic or recipient loops inside the webhook request. The provider event ID is the transport idempotency key.
2. **Business job queue:** the global `public.n8n_global_jobs` row is the durable work item after tenant scope is known. One job row holds request data, acknowledgement state, progress and bounded errors in JSONB. The CFCF worker claims a small bounded batch and processes recipients serially or with intentionally small concurrency. In-memory loops alone are not durable queues.

The shared-number path must resolve sender to exactly one authoritative CFCF tenant/contact before creating a tenant-scoped job. The tenant-owned path resolves tenant from trusted receiver/session mapping and ignores any payload-supplied `tenant_id`; then it checks the sender's contact/role. Since the registry requires `tenant_id`, an unknown shared-number sender cannot be inserted as a normal tenant job. Do not invent a tenant or guess a match.

Use two separate acknowledgement policies:

- **Transport HTTP acknowledgement (always required):** respond promptly to WAHA/provider; return 2xx only after durable enqueue succeeds or an already-enqueued duplicate is recognized. If persistence fails, return retryable non-2xx. This is transport-level and is not a WhatsApp message to the human sender. Never keep the webhook open while long business processing runs.
- **Human WhatsApp acknowledgement (conditional):** send one immediate receipt only when the operation will take longer than a normal interactive response or must continue asynchronously (e.g. reports, scheduled reminders, multi-recipient campaigns, or queued work). Send it only after durable enqueue, include a safe reference and clear “please don't resend” wording, and suppress duplicate receipts for the same provider event ID.
- **Quick operations:** when a request can safely finish within the normal interactive response window, skip the separate “queued” receipt and send the actual result after completion. If it becomes queued/asynchronous, switch to the long-running policy. Never report success before completion.
- Store acknowledgement policy/state in the job JSONB document when a job exists (e.g. not_required, pending, provider_accepted, failed, uncertain). Provider acceptance is not proof of receipt/read. Do not reveal tenant/contact existence to unknown senders.

Failure outcomes must be reviewable without blind retries:

- Before enqueue: no “queued” sender receipt; retryable transport failure.
- After enqueue but before any provider submission: preserve the same job; re-claim only when state proves no external submission occurred.
- Definitive provider rejection: record a safe failed status; retry only if the failure is classified transient and the action is known safe.
- Timeout/lost provider response after submission: mark `uncertain`, stop automatic resend, require manual review.
- Ambiguous sender-acknowledgement result: mark acknowledgement `uncertain`; do not blindly resend it.
- Execution failure: current **CFCF — Shared Error Handler** captures sanitized workflow/execution metadata and explicit review/no-blind-retry flags only. It is not a durable alert, job-state update, lease-release mechanism, or sender message. Once the registry is approved, append a bounded error event and a safe review flag to the same job JSONB row; expose status/reference to the manager PWA. Keep event history capped at 500.

Do not deduplicate distinct requests solely by message text. Use provider event IDs for transport deduplication and a scoped request ID for business-job idempotency. Keep queues/pacing independent per assigned WAHA session/manager; no cross-session fallback.

## Inbound provider-event idempotency — Batch 23

The registry draft now includes a partial unique index named `n8n_global_jobs_inbound_event_unique_idx` for `job_type = 'whatsapp_inbound'`, scoped by `product_id`, `tenant_id`, `provider_name`, trusted `session_name`, and `provider_event_id`. These values must be normalized from the authenticated provider event and authoritative routing context, never accepted as proof of identity from caller-supplied tenant fields.

Enqueue sequence for an inbound event:

1. Authenticate the inbound transport and validate required event fields.
2. Resolve the trusted receiving session and exactly one authoritative CFCF tenant/contact/role as applicable.
3. Build the provider event key from provider name, trusted session name, and provider event ID; check for an existing job in that scope.
4. Insert one `whatsapp_inbound` job with the key and validated event metadata. The unique index is the concurrency guard if two webhook executions race.
5. If insertion conflicts, fetch the existing job in the same product/tenant scope and return transport success without creating a second job or human sender receipt.
6. If insert fails for any reason other than a confirmed duplicate, return retryable non-2xx. Never return accepted/queued before the write commits.

The index is additive to the existing scoped `request_id` uniqueness. It does not replace request-level idempotency and does not authorize the sender. The migration remains draft-only and has not been applied to any database. No live enqueue or provider operation is implemented by this schema change.


## Inbound enqueue contract guards — Batch 24

Static repository tests now assert that the draft inbound-event uniqueness index is partial and scoped by product, tenant, provider, trusted session, and provider event ID; it applies only to whatsapp_inbound rows with all three event identity fields nonblank. The separate request_id uniqueness guard remains in place for business-job idempotency.

The tests also pin the required conflict behavior: only a confirmed duplicate may return the existing same-scope job with transport success; any other persistence error must remain retryable non-2xx. Event deduplication is not an authorization shortcut: ingress authentication and authoritative session/tenant/contact resolution must happen first.

These are repository-level contract tests only. They do not execute PostgreSQL, prove unique-index behavior against a live database, or implement the ingress queue. The migration remains draft-only, all relevant n8n workflows remain inactive, and no PWA notification objects are changed.


## Manager progress read-model security hardening — Batch 38

The draft migration now separates manager progress visibility from the private JSONB job document:

- `progress_summary` is a generated, allowlisted JSONB summary containing only validated numeric progress counters. Invalid/missing values become null rather than being cast unsafely.
- Authenticated managers receive column-level SELECT grants only for safe metadata and `progress_summary`; they do not receive SELECT on the full `job_data` column.
- `public.n8n_global_job_progress` is a read-only view with `security_invoker = true`, preserving the underlying table's tenant-owner RLS and column privileges.
- The view exposes job reference, product/tenant scope, type/status, timestamps, progress summary and a review flag. It does not expose raw `job_data`, recipient arrays, provider payloads, message text, phone numbers, event history or raw errors.
- The n8n service role remains the intended writer. PWA remains read-only.
- This is a draft migration and static contract only. It has not been applied or tested against a live database. Before any approval, verify the deployed PostgreSQL version supports the view option, confirm grants and RLS behavior in an approved non-production project, and test cross-tenant reads.
