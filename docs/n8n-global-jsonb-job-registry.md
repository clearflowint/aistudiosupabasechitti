# Global JSONB Job Registry — Batch 1

## Decision

Use one global table, `public.n8n_global_jobs`, for job tracking across ClearFlow products. Keep product-specific execution logic in separate n8n workflows. Product business data stays in its existing tables.

- One row represents one job.
- `job_id` is generated by PostgreSQL and starts at 100.
- `product_id`, `tenant_id`, `job_type`, `status`, and timestamps are searchable columns.
- `job_data` is the single JSONB document for the instruction (including `request_id`), prepared payload, recipients, per-recipient statuses, acknowledgement events, progress, errors and summary.
- No per-recipient delivery table, separate communication table, automation RPC, or generic database function is introduced.
- The PWA can read only jobs for its active product/tenant owner. n8n is the writer using server-side credentials, never browser code.

## Flow

1. The PWA sends the manager's instruction, product ID, tenant ID, action and selected IDs.
2. n8n validates the authenticated user's identity and confirms active owner access for the exact product/tenant before reading private data or writing a job.
3. n8n fetches authoritative data from existing Supabase tables, deduplicates recipients, and resolves the actual recipient count.
4. Before creating a job, n8n looks up the scoped `request_id`. If it already exists, return that job receipt and do not dispatch again. A unique expression index is the final race-condition guard; if a concurrent duplicate insert conflicts, fetch and return the existing job.
5. For a new approved production job, n8n creates one job row and uses the returned database `job_id` as the canonical Job ID.
6. n8n updates the same row's `status` and `job_data` as progress and acknowledgements arrive.
7. The PWA reads the row and displays progress. It does not prepare messages, reports, recipient payloads, or schedules.

## Campaign batch limit

A campaign batch contains 1–100 unique resolved contacts. n8n must reject a larger batch before any provider call. The database constraint also rejects any campaign job document that contains a `recipients` array longer than 100. Do not silently split a batch into multiple jobs.

## Example `job_data`

```json
{
  "request": {
    "action": "campaign",
    "group_ids": ["group-1"]
  },
  "progress": {
    "recipient_count": 2,
    "processed_count": 1,
    "accepted_count": 1,
    "failed_count": 0,
    "uncertain_count": 0
  },
  "recipients": [
    {"contact_id": "contact-1", "status": "provider_accepted", "updated_at": "2026-10-20T05:40:05Z"},
    {"contact_id": "contact-2", "status": "pending"}
  ],
  "events": [
    {"time": "2026-10-20T05:40:05Z", "contact_id": "contact-1", "event": "provider_accepted"}
  ],
  "result_summary": null,
  "error": null
}
```

Use statuses that reflect evidence. Provider acceptance is not proof of delivery or read. If a send outcome is uncertain, record `uncertain` and require manual reconciliation; do not blindly retry or resend.

## Update ownership

n8n is the only writer for a job's JSONB progress. Keep recipient processing and JSONB updates sequential within a job so simultaneous writes cannot overwrite one another. The PWA reads the saved document and does not mutate job state.
